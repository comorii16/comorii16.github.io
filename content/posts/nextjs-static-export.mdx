GitHub Pages는 정적 파일만 서빙합니다.
Node.js 프로세스가 없으니, Next.js를 올리려면 빌드 결과가 완전한 HTML/CSS/JS 묶음이어야 합니다.
이때 사용하는 것이 Static Export입니다.

## 설정

`next.config.ts`에 `output: 'export'`를 지정하면 `next build`가 `out/` 디렉터리를 만듭니다.

```typescript
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'export',
  trailingSlash: true,
  images: { unoptimized: true },
}

export default nextConfig
```

`trailingSlash: true`가 중요합니다.
이 옵션이 있으면 `/posts/hello-world/index.html` 형태로 파일이 생성되어,
정적 호스팅에서 URL을 직접 입력해도 해당 문서를 찾을 수 있습니다.

<Callout type="warning">
`trailingSlash` 없이 배포하면 새로고침이나 직접 접근 시 404가 나는 경우가 생깁니다.
정적 호스팅에서는 라우팅을 해줄 서버가 없다는 점을 계속 의식해야 합니다.
</Callout>

## 쓸 수 없는 기능

Static Export는 요청 시점에 동작하는 모든 것을 포기하는 대신 배포가 단순해집니다.
아래 기능은 사용할 수 없습니다.

| 기능 | 사용 가능 |
| --- | --- |
| SSR (요청 시 렌더링) | X |
| ISR (revalidate) | X |
| Server Actions | X |
| Middleware | X |
| Route Handler (GET 외) | X |
| 서버 기반 Image Optimization | X |

반대로 말하면, 빌드 시점에 결과가 정해지는 것은 모두 쓸 수 있습니다.
`generateStaticParams`로 경로를 미리 만들고, `generateMetadata`로 페이지별 메타데이터를 만드는 식입니다.

```typescript
export const dynamicParams = false

export function generateStaticParams() {
  return getPostSlugs().map((slug) => ({ slug }))
}
```

## 이미지

`next/image`의 최적화는 서버가 필요합니다.
정적 배포에서는 `images.unoptimized`를 켜서 원본을 그대로 내보내거나,
아예 `<img>`를 쓰고 이미지를 미리 WebP로 준비하는 편이 단순합니다.

## Route Handler로 RSS 만들기

GET 요청만 처리하고 `dynamic = 'force-static'`을 지정하면,
Route Handler도 빌드 시점에 파일로 떨어집니다.

```typescript
export const dynamic = 'force-static'

export function GET() {
  return new Response(buildRssXml(), {
    headers: { 'Content-Type': 'application/rss+xml; charset=utf-8' },
  })
}
```

## 정리

- 정적 호스팅에 올릴 거라면 `output: 'export'`와 `trailingSlash: true`를 함께 쓴다
- 요청 시점 기능은 처음부터 설계에서 제외한다
- 대신 빌드 시점에 할 수 있는 일은 최대한 빌드로 옮긴다

제약이 분명한 대신 배포 파이프라인이 아주 단순해집니다.
push 한 번으로 끝나는 블로그에는 잘 맞는 선택입니다.
